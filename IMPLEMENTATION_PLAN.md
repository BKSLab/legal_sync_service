Цель — довести сервис до MVP без расползания задач и преждевременной реализации

## 1. Проверить publication.pravo.gov.ru

Цель: подтвердить, что мониторинг можно построить на реальном API, а не на
предположениях из ТЗ.

Решение по MVP:

- мониторим блок `president` для федеральных законов;
- мониторим блок `government` для постановлений Правительства РФ;
- внутри блоков дополнительно фильтруем по `DocumentTypes`, потому что один
  блок может содержать несколько видов актов (например, `government` содержит
  и постановления, и распоряжения);
- остальные блоки не входят в MVP.

Подтвержденные `DocumentTypeId`:

- Федеральный закон: `82a8bf1c-3bc7-47ed-827f-7affd43a7f27`
- Постановление Правительства РФ: `fd5a8766-f6fd-4ac2-8fd9-66f414d314ac`

Что сделать:

- Проверить `GET /api/Documents` на реальных параметрах:
  - `PeriodType=daily`
  - `Block=president|government`
  - `DocumentTypes=<GUID вида документа>`
  - `PageSize=10|30|100|200`
- Зафиксировать реальный формат ответа:
  - список документов лежит в `items`;
  - как называются поля `eoNumber`, `name`, `complexName`, `documentDate`, `id`;
  - как работает пагинация.
- Подтвердить URL скачивания PDF по `eoNumber`.
  - `/File/GetFile/{eoNumber}` проверен и возвращает 404.
  - На странице `/document/{eoNumber}` обнаружена ссылка:
    `/file/pdf?eoNumber={eoNumber}`.
  - На странице также используется текстовый endpoint:
    `/api/DocumentText?eonumber={eoNumber}`.
- Проверить справочные endpoints:
  - `/api/PublicBlocks`
  - `/api/Categories?block=...`
  - `/api/SignatoryAuthorities`
  - `/api/DocumentTypes`
  - `/api/Document?eoNumber=...`
  - `/api/BlockStatistics/daily`
- Сохранить 1-2 JSON/PDF-фикстуры для unit/integration-тестов парсинга.

Критерий готовности:

- Есть тест клиента `PublicationPravoClient` на реальном формате ответа.
- Есть зафиксированный рабочий URL скачивания PDF.
- Открытый вопрос #1 из `specification.md` закрыт.
- Открытый вопрос #8 из `specification.md` закрыт для MVP.
- GUID видов документов для `Федеральный закон` и `Постановление` зафиксированы

## 3. Зафиксировать workflow статусов

Рекомендуемое решение для MVP: ручной review обязателен.

Базовый поток:

```text
draft -> scheduled -> processing -> sent
                         |
                         -> failed

draft -> cancelled
```

Пояснение:

- `draft` создаётся автоматически или вручную после обнаружения изменения.
- Оператор проверяет событие и подтверждает его.
- Подтверждение сразу переводит событие в `scheduled`; отдельный `approved`
  можно оставить в enum для будущего, но не использовать в MVP.
- `send_at` равен дате вступления изменений в силу.

Критерий готовности:

- В сервисном слое запрещены недопустимые переходы.
- API и админка показывают понятные статусы.
- Открытые вопросы #3 и #4 из `specification.md` закрыты решением.

## 4. Собрать первый вертикальный сценарий

Цель: получить работающий сквозной поток без автоматического мониторинга.

Сценарий:

1. Оператор создаёт `tracked_document`.
2. Оператор вручную создаёт `legal_change`.
3. Оператор подтверждает событие.
4. Сервис выбирает `scheduled`-событие с `send_at <= now()`.
5. Сервис получает текст консолидированной редакции.
6. Сервис извлекает статью.
7. Сервис отправляет статью в RAG Service.
8. Событие получает статус `sent` или `failed`.

Критерий готовности:

- Есть сервис обработки одного `LegalChange`.
- Есть endpoint или admin-action ручного запуска обработки.
- Есть тест на успешную обработку и на ошибку отправки.

## 5. Реализовать анализ закона-поправки

Цель: автоматически создавать `draft`-события из текста закона-поправки.

Что сделать:

- Скачать PDF закона-поправки по `eoNumber`.
- Извлечь текст через `pdfplumber`.
- Нормализовать текст.
- Regex-правилами извлечь:
  - номера изменяемых статей;
  - дату вступления в силу;
  - фрагмент поправки по каждой статье.
- Если дата не определена, создавать `draft` без `effective_date`.
- LLM не подключать до появления реальных случаев, где regex/правила недостаточны.

Критерий готовности:

- Есть unit-тесты на фикстурах законов-поправок.
- Для каждого найденного изменения создаётся отдельный `LegalChange`.
- Повторный запуск не создаёт дубликаты.

## 6. Реализовать извлечение статьи из консолидированной редакции

Цель: детерминированно получать актуальный текст конкретной статьи.

Модули:

- `services/document_fetcher.py` — получение HTML/PDF/DOCX.
- `utils/text_normalization.py` — нормализация текста.
- `services/section_extractor.py` — поиск и извлечение статьи.

Приоритет методов:

1. DOM-якоря / структурированный HTML.
2. CSS/XPath-селекторы.
3. Regex по заголовкам `Статья N`.
4. Структурные правила.
5. LLM только как ручной fallback, не для автоматической отправки.

Критерий готовности:

- Статья извлекается без изменения юридического текста.
- Ошибки извлечения переводят событие в `failed`.
- Есть тесты на нормальную статью, последнюю статью документа и не найденную статью.

## 7. Сверить контракт RAG Service

Цель: исключить расхождение между ожидаемым и фактическим API RAG.

Что проверить:

- URL: `PUT /api/v1/document/{document_id}/sections/{section_number}`.
- Заголовок авторизации.
- Обязательные поля payload.
- Формат успешного ответа.
- Поведение при повторной отправке той же статьи.
- Формат ошибок.

Критерий готовности:

- `RagClient` покрыт тестами через `httpx.MockTransport`.
- Успешный ответ сохраняется в `rag_response`.
- Ошибка сохраняется в `last_error`, `retry_count` увеличивается.

Цель: заменить ручное создание событий автоматическим daily-процессом.

- Подключить его к APScheduler.
- Реализовать `ProcessingService` для выборки `scheduled`-событий.

Рекомендуемая retry-стратегия для MVP:

- максимум 3 попытки;
- экспоненциальная задержка;
- после исчерпания попыток статус остаётся `failed`;

Критерий готовности:

- Повторный мониторинг идемпотентен.
- Ошибка одной статьи не блокирует остальные.

## Не входит в MVP

- Поддержка приложений, пунктов и частей как отдельных структурных единиц.
- Автоматическое принятие решений LLM без ручной проверки.
- Несколько источников консолидированной редакции на один документ.
- Полноценный UI поверх sqladmin.
- Хранение и просмотр логов в БД, пока не принято решение по вопросу #7.
