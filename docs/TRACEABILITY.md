# Сквозная история документа

В админке откройте **«Путь документа»** (`/admin/document-trace`) и выберите
`document_id`. Страница связывает постановку на контроль, проверки источника,
найденные изменения, решение оператора, очередь, все попытки отправки и этапы
обработки в RAG. История RAG читается по API при открытии страницы; если RAG
недоступен или ещё не обновлён, история Legal Sync остаётся доступной.

## Идентификаторы

| Поле | Назначение |
| --- | --- |
| `document_id` | Общий идентификатор документа в двух сервисах |
| `tracked_documents.rag_ingestion_id` | Операция первоначальной загрузки, поставившая документ на контроль |
| `legal_changes.monitoring_check_id` | Проверка, обнаружившая изменение; переход в её журнал |
| `legal_changes.id` | Изменение статьи, передаётся в `X-Legal-Sync-Change-ID` |
| `delivery_attempts.id` | Новая UUID для каждой попытки; передаётся в `X-Request-ID` |
| `operation_id` | UUID обработки на стороне RAG; возвращается после выполнения |
| `input_sha256` | Контрольная сумма UTF-8 текста статьи, независимо вычисляемая обоими сервисами |

Попытка доставки записывается отдельной транзакцией **до HTTP-запроса**.
Сохраняются подготовка текста, контрольная сумма, начало отправки, HTTP-статус,
подтверждение RAG и время сохранения ответа. Полный текст, API-ключи и заголовки
авторизации в новый журнал не записываются. Повтор создаёт новую попытку,
не перезаписывая предыдущую.

## Как читать результат

- **Коллекция обновлена**: получено подтверждение RAG с проверкой целостности,
  совпадают документ, статья, редакция и контрольная сумма текста.
- **Обновлено с предупреждениями**: коллекция проверена, но есть проблема
  сопутствующего действия; откройте этапы RAG.
- **Исход неизвестен**: таймаут, отмена запроса или остановка отправителя.
  RAG мог продолжить работу. Найдите обработку по номеру попытки, прежде чем
  делать вывод о результате. Очередь сохраняет существующую политику повторов.
- **Получен ответ без подтверждения этапов**: ответ старой версии RAG;
  он не доказывает прохождение новых проверок журнала.
- **Ошибка / отклонено / отложено / приостановлено**: причина и последний
  этап отображаются в попытке. Ошибка после записи не означает откат Qdrant.

В RAG журнал `/admin/ingestion-log` показывает очередь документа, проверку
редакции, разбор, чанки, обогащение, векторы, запись и проверку Qdrant,
снятие старой редакции, сохранение реестра/журнала и постановку на контроль.
Счётчики долгих этапов сохраняются каждые 5 секунд. «Нет сигнала» после минуты
без обновлений означает неизвестный исход, а не доказанное завершение.

## Настройка и обновление

В Legal Sync нужен существующий `RAG_SERVICE_BASE_URL` и `RAG_SERVICE_API_KEY`.
Новый защищённый маршрут RAG: `GET /api/v1/ingestion-runs?document_id=...`,
с фильтром `request_id` и пагинацией. Используется тот же API-ключ.

Для переходов браузером задайте `RAG_ADMIN_BASE_URL` в Legal Sync и
`LEGAL_SYNC_ADMIN_BASE_URL` в RAG: адрес сервиса, доступный оператору, **без**
суффикса `/admin`. Внутренний Docker-адрес для HTTP-обмена может отличаться.
Без публичного адреса история по API работает, внешние ссылки скрыты.
У админок отдельные cookies, поэтому вход в одну не завершает сессию другой
при работе на одном IP с разными портами. После обновления потребуется войти заново.

Миграция Legal Sync `20260921_0005` добавляет таблицу попыток и две связи.
Миграция RAG `20260921_1200` добавляет независимую таблицу операций. Они не
удаляют документы, коллекции, поисковые запросы, вопросы и ответы.

При обновлении старого production RAG необходимо отдельно учесть уже
существующую миграцию `20260907_1300`: она удаляет старый реестр `documents`.
Переход с очисткой базы знаний требует согласованного переноса; сохраняются
`search_logs`, `vera_chat_sessions`, `vera_chat_turns`, `vera_message_feedback`
и `vera_session_feedback`. Эта доработка не выполняет такую очистку.

История появляется для новых операций. Старым отправкам и регистрациям
идентификаторы и этапы задним числом не придумываются. Запросы, отклонённые
до входа в обработчик RAG (например, API-валидация 422), видны на стороне
Legal Sync как HTTP-ответ попытки, без вымышленной операции индексации.

## Проверка реализации, 21.09.2026

Пройдены 174 теста Legal Sync и 359 тестов RAG; затронутые проверки повторены
после последних изменений. Отдельный HTTP-прогон двух сервисов с изолированными
PostgreSQL и Qdrant прошёл всю цепочку: загрузка → регистрация → обнаружение
изменения → согласование → доставка → проверка чанков. Правовой портал и
платные модели в этом прогоне заменены фиксированными тестовыми ответами.

Проверены совпадение номера попытки и SHA-256, сохранность `search_logs` при
новой миграции, загрузка через форму, одновременный вход в две админки,
настольное и мобильное отображение. Production в этом прогоне не использовался.
