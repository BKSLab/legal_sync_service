# Исследование источника консолидированных редакций pravo.gov.ru

Дата исследования: 2026-08-05.

## Цель

Проверить, можно ли использовать официальный банк «Законодательство России» на
`pravo.gov.ru` для автоматического получения актуальных редакций отслеживаемых
нормативных актов, например Трудового кодекса РФ.

Этот источник решает другую задачу, чем `publication.pravo.gov.ru`:

- `publication.pravo.gov.ru` используется для ежедневного обнаружения новых
  официальных публикаций и актов-поправок;
- `pravo.gov.ru/proxy/ips/` рассматривается как источник текста исходного НПА с
  уже внесенными изменениями.

Официальный портал указывает, что размещенные в банке «Законодательство России»
тексты федеральных законов и ряда других актов с внесенными изменениями имеют
официальный статус:

- <https://pravo.gov.ru/>
- <http://pravo.gov.ru/proxy/ips/?start_search&fattrib=1>

## Краткий вывод

Источник предварительно пригоден. Поиск документов работает обычными HTTP GET-
запросами и не требует обязательного JavaScript-рендеринга. Для поиска и разбора
выдачи достаточно `httpx` и `BeautifulSoup`.

При этом интерфейс старый и технически неудобный:

- страница и параметры поиска используют `Windows-1251`;
- выдача состоит из нескольких `frameset`/`iframe`;
- названия параметров непрозрачны (`a1`, `a8`, `nd`, `rdk`);
- сервер периодически отвечает очень медленно;
- выбор редакции и DOM полного текста требуют отдельного PoC.

Playwright следует оставить только как fallback. Начинать реализацию нужно с
прямых HTTP-запросов.

## Проверенная форма расширенного поиска

Стартовая страница:

```text
GET http://pravo.gov.ru/proxy/ips/?start_search&fattrib=1
```

Ответ:

```text
HTTP 200
Content-Type: text/html
HTML charset: windows-1251
```

На странице находится обычная форма:

```html
<form action="?" method="GET" id="filterform">
```

Подтвержденные поля формы:

| Параметр | Назначение |
|---|---|
| `bpas` | Банк правовых актов; для федерального законодательства использовалось `cd00000` |
| `a3` | Вид акта, значение выбирается из классификатора |
| `a6` | Принявший орган, значение выбирается из классификатора |
| `a15` | Принявший субъект |
| `a7type` | Режим поиска по дате |
| `a7from` | Начало диапазона даты подписания |
| `a7to` | Конец диапазона даты подписания |
| `a7date` | Одна дата подписания |
| `a8` | Номер документа |
| `a8type` | Режим поиска по номеру |
| `a1` | Наименование документа |
| `a0` | Поиск по тексту документа |
| `a16` | Подписи |
| `a17` | Публикации в периодических изданиях |
| `a4` | Состояние документа |
| `a23` | Ключевые слова |
| `textpres` | Наличие текста; `yes` означает «только с текстом» |
| `sort` | Порядок сортировки |

Для `a8type` в форме подтверждены как минимум значения:

```text
2 — точное совпадение
3 — содержит
```

## Критичная особенность кодировки

Значения на русском языке необходимо передавать как percent-encoded байты
`Windows-1251`, а не как обычный UTF-8 query string.

UTF-8-запрос с корректными реквизитами ТК РФ вернул ложный результат:

```text
Не найдено ни одного документа, сформулируйте запрос по-другому
```

Тот же запрос с кодированием `Windows-1251` успешно нашел документ.

Минимальный Python-helper:

```python
from urllib.parse import quote_from_bytes


def quote_cp1251(value: str) -> str:
    return quote_from_bytes(value.encode("cp1251"))
```

Query string безопаснее собирать явно, чтобы HTTP-клиент повторно не перекодировал
уже подготовленные значения. Ответы также нужно декодировать как `cp1251`, если
клиент не определил кодировку автоматически.

## Проверенный поиск Трудового кодекса РФ

Использованные реквизиты:

```text
Наименование: Трудовой кодекс Российской Федерации
Номер: 197-ФЗ
Банк: cd00000
Только документы с текстом: yes
```

Параметры запроса до percent-encoding:

```text
searchres=
bpas=cd00000
a8=197-ФЗ
a8type=2
a1=Трудовой кодекс Российской Федерации
textpres=yes
sort=1
```

Запрос успешно вернул единственный нужный документ:

```text
Кодекс Российской Федерации от 30.12.2001 № 197-ФЗ
nd=102074279
```

Ссылка из результата:

```text
http://pravo.gov.ru/proxy/ips/?docbody=&link_id=0&nd=102074279&firstDoc=1
```

Параметр `nd` является стабильным внутренним идентификатором документа в ИПС.
Для ТК РФ подтверждено значение:

```text
102074279
```

После первичного поиска `nd` следует сохранять в `tracked_documents`. Повторно
искать документ по форме при каждом обновлении не требуется.

## Фактическая цепочка страниц поиска

Интерфейс использует вложенные фреймы. Проверенная последовательность:

```text
1. ?start_search&fattrib=1
   Форма расширенного поиска.

2. ?searchres=&bpas=...&a1=...&a8=...
   Возвращает frameset, а не сами результаты.

3. ?searchlist=&bpas=...&a1=...&a8=...
   Возвращает оболочку списка и iframe с id="list".

4. ?list_itself=&bpas=...&a1=...&a8=...&page=firstlast
   Возвращает реальные элементы списка документов.

5. ?docbody=&link_id=0&nd=102074279&firstDoc=1
   Открывает документ.

6. ?doc_itself=&nd=102074279&page=1&rdk=...
   Предполагаемый прямой endpoint страницы текста конкретной редакции.
```

На шаге 3 URL шага 4 можно получить из:

```html
<iframe id="list" src="...">
```

На шаге 4 документы представлены ссылками, содержащими `nd`:

```html
<a href="?docbody=&link_id=0&nd=102074279&firstDoc=1">
```

Для парсинга выдачи достаточно:

```python
from bs4 import BeautifulSoup
from urllib.parse import parse_qs, urlparse

soup = BeautifulSoup(html, "lxml")
list_url = soup.select_one("iframe#list[src]")["src"]

for link in soup.select('a[href*="nd="]'):
    query = parse_qs(urlparse(link["href"]).query)
    nd = query.get("nd", [None])[0]
```

## Пагинация списка результатов

Список по умолчанию выводит 20 документов. Следующая страница задается параметром:

```text
start=20
```

В интерфейсе доступны размеры страницы:

```text
5, 10, 20, 50, 100, 200
```

При поиске по номеру `197-ФЗ` в режиме «содержит» портал вернул 27 разных
федеральных законов. Поэтому номер без даты и названия недостаточен для надежной
идентификации документа.

Рекомендуемые реквизиты первичного поиска:

1. точный номер;
2. дата подписания;
3. полное наименование;
4. вид документа;
5. проверка полученной карточки перед сохранением `nd`.

## Документ и редакции

В ссылках ИПС используются параметры:

| Параметр | Наблюдаемое назначение |
|---|---|
| `nd` | Идентификатор нормативного акта |
| `rdk` | Идентификатор редакции |
| `page` | Номер страницы текста документа |
| `docbody` | Оболочка просмотра документа |
| `doc_itself` | Непосредственное содержимое страницы документа |
| `vkart=card` | Карточка документа |
| `vkart=ref` | Справочная информация/связи документа |

В открытых ссылках встречаются адреса вида:

```text
http://pravo.gov.ru/proxy/ips/?doc_itself=&nd=102074279&page=1&rdk=134
```

Это подтверждает наличие адресуемых редакций. Однако в ходе исследования
прямые запросы полного `docbody`/`doc_itself` для ТК РФ периодически зависали.
Поэтому пока не подтверждены окончательно:

- DOM текста статьи;
- endpoint списка всех редакций;
- правило выбора текущего `rdk`;
- соответствие `rdk` конкретной дате начала действия;
- количество страниц ТК РФ и способ перехода между ними.

Эти пункты нельзя считать готовым контрактом — их должен закрыть отдельный PoC.

## Как выбирать редакцию

Нельзя безусловно брать самую последнюю редакцию на момент HTTP-запроса.

Сервис должен выбрать редакцию, которая действует на `legal_change.effective_date`.
Это важно при повторной обработке: если отправка была отложена, на портале уже
может находиться более поздняя редакция с другими изменениями.

Целевой алгоритм:

1. получить список редакций документа по сохраненному `nd`;
2. для каждой редакции определить период действия;
3. выбрать редакцию, действующую на `effective_date`;
4. сохранить выбранные `nd`, `rdk`, дату редакции и URL источника в событии;
5. скачать все требуемые страницы;
6. извлечь статью без изменения юридического текста.

Если портал не дает надежно связать `rdk` с датой, автоматическую отправку нужно
останавливать и переводить событие на ручную проверку.

## Рекомендованная архитектура клиента

Предлагаемый отдельный клиент:

```text
app/clients/pravo_ips.py
```

Предполагаемые методы:

```python
search_documents(title, number, document_date) -> list[IpsDocument]
get_document_card(nd) -> IpsDocumentCard
get_revisions(nd) -> list[IpsRevision]
get_revision_pages(nd, rdk) -> list[str]
get_revision_html(nd, rdk) -> str
```

Технические требования:

- один `httpx.AsyncClient` с cookie jar на всю последовательность запросов;
- явная работа с `cp1251`;
- ручная сборка query string для русских параметров;
- timeout на каждый запрос;
- ограниченные retry только для сетевых ошибок и `5xx`;
- проверка `Content-Type` и минимальной ожидаемой структуры HTML;
- защита от циклических iframe и бесконечной пагинации;
- сохранение HTML-фикстур для тестов;
- логирование URL без полного текста документа;
- ограничение параллелизма, чтобы не перегружать официальный портал.

## Карта используемых библиотек

На первом этапе новые зависимости добавлять не требуется: необходимые библиотеки
уже присутствуют в проекте или входят в стандартную библиотеку Python.

| Этап | Библиотека | Как используется |
|---|---|---|
| HTTP-доступ к форме, списку и документу | `httpx` | Асинхронные GET-запросы, cookie jar на всю цепочку iframe, redirects, timeout, проверка статуса и `Content-Type` |
| Кодирование русских query-параметров | `urllib.parse` | `quote_from_bytes(value.encode("cp1251"))`, ручная сборка query string и разбор параметров URL |
| Декодирование ответов | стандартные `bytes`/`str` | Явное декодирование `response.content.decode("cp1251")`, если кодировка ответа не определилась корректно |
| Разбор HTML | `BeautifulSoup4` | Поиск формы, `iframe#list`, ссылок с `nd`, элементов списка редакций и контейнера текста документа |
| HTML parser для BeautifulSoup | `lxml` | Используется как backend: `BeautifulSoup(html, "lxml")` |
| Извлечение `nd`, `rdk`, `page` | `urllib.parse` | `urlparse()` и `parse_qs()` вместо ручного разбора строк |
| Нормализация пробелов и поиск границ статьи | `re` | Осторожные регулярные выражения после извлечения текста из DOM; юридический текст не переформулируется |
| DTO клиента ИПС | `Pydantic` | Структуры результата поиска, карточки документа, редакции и страницы текста |
| Хранение идентификатора и выбранной редакции | `SQLAlchemy` | Сохранение `nd`, `rdk`, даты редакции и URL источника в PostgreSQL |
| Плановый запуск | `APScheduler` | Запуск получения редакции для событий с `status=scheduled` и `send_at <= now()` |
| Логи и диагностика | стандартный `logging` | Этап запроса, `nd`, `rdk`, номер страницы, длительность и тип ошибки; полный юридический текст в лог не пишется |
| Unit-тесты | `pytest`, `pytest-asyncio` | Асинхронные тесты клиента и парсера |
| Подмена HTTP в тестах | `httpx.MockTransport` | Проверка запросов и ответов без обращения к pravo.gov.ru |
| HTML-фикстуры | файлы в `fixtures/` | Сохраненные ответы формы, выдачи, списка редакций и страниц документа для воспроизводимых тестов |

Резервные инструменты:

| Ситуация | Библиотека | Условие использования |
|---|---|---|
| Страница действительно требует выполнение JavaScript | `Playwright` | Только если нужные данные невозможно получить прямым HTTP-запросом |
| ИПС возвращает ссылку на PDF | `pdfplumber` | Только для PDF с текстовым слоем; image-only PDF автоматически не принимается как источник текста |
| ИПС возвращает ссылку на DOCX | `python-docx` | Извлечение текста при отсутствии структурированного HTML |

Распределение ответственности в коде:

```text
PravoIpsClient (httpx + urllib.parse)
    -> получает HTML и проходит цепочку iframe

PravoIpsParser (BeautifulSoup + lxml)
    -> извлекает документы, nd, редакции, rdk и страницы

SectionExtractor (BeautifulSoup + re)
    -> извлекает конкретную статью без изменения ее текста

ProcessingService (SQLAlchemy + RagClient)
    -> выбирает событие, фиксирует редакцию и отправляет статью в RAG

APScheduler
    -> только запускает ProcessingService по расписанию
```

Для retry на первом этапе отдельная библиотека не нужна. Ограниченное количество
повторов можно реализовать в клиенте обычным циклом только для timeout, сетевых
ошибок и ответов `5xx`. Если политика повторов станет общей и сложной, отдельно
рассмотреть `tenacity`, но не добавлять ее заранее.

## BeautifulSoup или Playwright

Рекомендуемый порядок:

1. `httpx + BeautifulSoup/lxml` — основной путь;
2. Playwright — только если конкретный шаг невозможно воспроизвести HTTP-запросом;
3. при изменении DOM — ошибка и ручная проверка, а не молчаливое извлечение
   потенциально неверного текста.

Почему BeautifulSoup подходит:

- форма отправляется GET-запросом;
- сервер возвращает готовый HTML;
- URL вложенных iframe присутствуют в разметке;
- результаты содержат обычные ссылки с `nd`;
- JavaScript в основном управляет интерфейсом, а не является единственным
  источником данных.

## Дополнительное направление: новый endpoint ips.pravo.gov.ru

В поисковой выдаче обнаружены страницы вида:

```text
https://ips.pravo.gov.ru/api/ips/legislation/document?baseid=None&hash=<sha256-подобное значение>
```

Они возвращают индексируемый полнотекстовый HTML консолидированных актов. Это
может оказаться более удобным источником, чем старый `/proxy/ips/`.

На текущем этапе не найден публичный способ:

- искать документ через этот API;
- преобразовать известный `nd` в `hash`;
- получить список редакций и их даты;
- подтвердить стабильность endpoint как официального API-контракта.

Поэтому этот endpoint следует исследовать отдельно, но пока не строить на нем
основную реализацию.

## Следующий PoC

Минимальная исследовательская реализация должна работать только с ТК РФ и
доказать следующий сценарий:

```text
поиск по реквизитам
    -> nd=102074279
    -> список редакций
    -> редакция на выбранную дату
    -> все страницы редакции
    -> извлечение одной заранее известной статьи
```

Критерии успешности PoC:

- повторный поиск стабильно возвращает тот же `nd`;
- редакция однозначно выбирается по дате;
- текст статьи извлекается полностью и без преобразования юридического текста;
- повторный запрос возвращает тот же результат;
- сохранены HTML-фикстуры формы, списка, редакций и страницы документа;
- тесты выполняются без доступа к сети на фикстурах.

До выполнения этого PoC источник следует считать перспективным, но не полностью
подтвержденным для автоматической отправки данных в RAG.
