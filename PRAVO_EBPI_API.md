# Источник машинного текста НПА: API actual.pravo.gov.ru (ebpi)

Дата исследования: 2026-09-07. Все факты ниже проверены живыми запросами.

Это материалы исследования на указанную дату. Текущий набор запросов сервиса,
правила отбора редакций и извлечения статей описаны в
[README.md](README.md#portal-contract); не все маршруты ниже используются
мониторингом.

Этот документ закрывает главный блокирующий вопрос проекта: где брать машинный
текст актов-поправок и актуальных консолидированных редакций.

Он **отменяет** выводы `PRAVO_CONSOLIDATED_RESEARCH.md` (старый ИПС
`pravo.gov.ru/proxy/ips/`, cp1251, frameset, Playwright) и раздел про OCR/PDF в
`PROJECT_CONTEXT.md`. Ни ИПС, ни PDF, ни OCR, ни LLM для разбора текста не нужны.

---

## 1. Главное открытие

`GET publication.pravo.gov.ru/api/DocumentText?eonumber=<eo>` — это **не текст**.
Это булев флаг «есть ли машинный текст». Ранее полученный `false` был не отказом
API, а корректным ответом «у этого скана текста нет».

Проверено на странице документа:

```js
$.ajax({ url: "/api/DocumentText?eonumber=0001202608040069",
         success: function (result) { if (result) { $('#doc_text').show(); } } });
```

Флаг всего лишь показывает ссылку «Текст правового акта», ведущую на:

```text
http://actual.pravo.gov.ru/content/content.html#pnum=<eoNumber>
```

За этой страницей стоит полноценный JSON API.

## 2. Базовый URL API

Из `http://actual.pravo.gov.ru/config.js`:

```text
HTTP_HOST     = 'http://actual.pravo.gov.ru:8000/api/ebpi/'
DEFAULT_BASE  = 'ebpi'
```

Обратите внимание на **порт 8000**. Во все запросы передаётся `bpa=ebpi`.

Банк данных (`bpainfo`): `276366 актов с 16.01.1990 по 05.09.2026`.
Подзаголовок портала: «Тексты правовых актов с внесенными изменениями
(с учетом изменений после 01.07.2022)».

Это официальный банк консолидированных редакций — то есть **один источник
закрывает обе задачи**: и текст акта-поправки, и актуальную редакцию
отслеживаемого НПА.

## 3. Контракт API

Все методы — `GET`, ответ `application/json; charset=utf-8`.

| Метод | Параметры | Назначение |
|---|---|---|
| `bpainfo` | `bpa` | Сведения о банке (объём, покрытие дат) |
| `attrsearch/` | `bpa`, `q=<JSON>` | Поиск документа по реквизитам |
| `card/` | `bpa`, `t=<JSON>` | Карточка документа по `pnum` или `hash` |
| `cardfull/` | `bpa`, `t=<hash>` | Расширенная карточка |
| `redactions/` | `bpa`, `t=<JSON>` | **Список редакций документа с датами** |
| `redtext` | `bpa`, `t=<redid>`, `ttl` | **HTML полного текста редакции** |
| `getcontent/` | `bpa`, `rdk=<redid>` | **Структурное оглавление редакции** |
| `glossary/` | `bpa`, `t=<dict>` | Словари (виды актов, состояния) |

### 3.1. `card/` — eoNumber в внутренние идентификаторы

```text
GET /api/ebpi/card/?bpa=ebpi&t={"pnum":"0001202608040069"}
```

```json
{
  "docid": 332572,
  "docstate": "Действует без изменений",
  "docpassing": "Федеральный закон от 04.08.2026 № 326-ФЗ",
  "docname": "О внесении изменений в статьи 7 и 17 ...",
  "dochash": "3576fd8ff6a3976d51942cf22c6c3c750ffb0ca28c3d666cf6bbb4bf81839e65",
  "docimagepath": "http://publication.pravo.gov.ru/Document/View/0001202608040069",
  "adoptions": [{"onumber": "326-ФЗ", "odate": "04.08.2026", "type": "Федеральный закон"}],
  "publications": ["...", "..."]
}
```

`pnum` — это ровно `eoNumber` из publication.pravo.gov.ru. Это и есть шов между
двумя системами. `dochash` — стабильный глобальный идентификатор акта.

**Проверено:** для ФЗ от 26.07.2026 № 246-ФЗ (`eoNumber=0001202607260006`) и
ФЗ от 25.05.2026 № 144-ФЗ (`eoNumber=0001202605250023`) полученные `dochash`
побайтово совпали с `gohash` в тексте ТК РФ (см. п. 3.5).

### 3.2. `attrsearch/` — первичный поиск отслеживаемого документа

```text
GET /api/ebpi/attrsearch/?bpa=ebpi&q=<urlencoded JSON array>
```

Каждый элемент массива — атрибут поиска:

| AttrId | Атрибут | Формат |
|---|---|---|
| 4 | Вид акта | `AttrMode=1`, `IDParams=[{Id,Param}]` |
| 5 | Дата подписания | `DateFrom`/`DateTo` = `YYYYMMDD` |
| 6 | Номер | `AttrMode=0` точный, `8` по началу; `Words=["197-ФЗ"]` |
| 7 | Наименование | `AttrMode=9`; `Words=["+трудовой","+кодекс"]` |
| 14 | Состояние | `AttrMode=1`, `IDParams` |
| 999 | **Сортировка/пагинация (обязательный)** | `AttrMode=<page>`, `Words=[limit, sort, "20220701", 0, 1]` |

Атрибут `999` обязателен, а `AttrMode` в нём — **номер страницы, начиная с 1**.
При `page=0` приходит `docscount`, но пустой `docs` — это и сбивало с толку.

Проверенный запрос для ТК РФ:

```json
[{"AttrId":6,"AttrMode":0,"Words":["197-ФЗ"]},
 {"AttrId":7,"AttrMode":9,"Words":["+трудовой","+кодекс"]},
 {"AttrId":999,"AttrMode":1,"Words":[20,"date","20220701",0,1]}]
```

Результат — ровно один документ:

```json
{"docid": 64284,
 "docpassing": "Кодекс Российской Федерации от 30.12.2001 № 197-ФЗ",
 "docnames": "Трудовой кодекс Российской Федерации",
 "docstate": "Действует с изменениями",
 "docpass0date": "20011230", "docpass0number": "197-ФЗ",
 "dochash": "03bdee8f44a71247d7ba3342484326dbc3fa292d3caae9f88ada4b1ee38c20d9"}
```

`dochash` сохраняется в `tracked_documents` один раз; повторный поиск не нужен.

### 3.3. `redactions/` — список редакций с датами

```text
GET /api/ebpi/redactions/?bpa=ebpi&t={"hash":"03bdee...","ttl":3}
```

`ttl` управляет глубиной выборки:

| ttl | Что возвращает (для ТК РФ) |
|---|---|
| `0` | 39 редакций — с `ACTUAL_START_DATE=20220701` |
| `2` | работает для запроса по `pnum`, не по `hash` |
| `3` | **199 редакций — полная история** |
| `4` | 38 редакций — актуальный режим |

Элемент списка:

```json
{"redid": 495396,
 "reddocrefid": 282629,
 "reddate": "20270301",
 "reddatetimed": "2027-03-01T00:00:00",
 "statename": "Действует с изменениями",
 "redcaption": "199. на 01.03.2027 (№ 246-ФЗ от 26.07.2026), не вступившая в силу редакция",
 "redstatus": "актуальная",
 "actual": false,
 "redcompleted": true,
 "hascontent": true}
```

Ключевые факты:

- **`reddate` (YYYYMMDD) — дата вступления редакции в силу.** Это прямо закрывает
  вопрос, который старое исследование считало неподтверждённым («не подтверждено
  соответствие `rdk` конкретной дате»). Выбор редакции на `effective_date` —
  это просто `max(reddate) <= effective_date`.
- `actual: true` помечает действующую сейчас редакцию.
- `redcaption` содержит номер и дату акта-поправки.
- **Будущие редакции публикуются заранее** (`не вступившая в силу редакция`).
  Сервису не нужно ждать даты вступления, чтобы узнать будущий текст, — можно
  подготовить его заранее и отправить в RAG строго в `reddate`.

### 3.4. `redtext` — полный текст редакции

```text
GET /api/ebpi/redtext?bpa=ebpi&t=<redid>&ttl=0
```

Ответ: `{"redtext": "<html>...</html>", "error": null}`.

Проверено на ТК РФ, редакция 495396: 2 150 057 байт ответа, 1 332 213 символов
HTML, 954 628 символов чистого текста, 541 статья. На небольшом ФЗ 326-ФЗ —
23 217 символов HTML, полный корректный текст закона.

Разметка чистая и семантическая:

```html
<p class="T" id="p2374">Раздел I. ОБЩИЕ ПОЛОЖЕНИЯ</p>
<p class="H" id="p2375">Глава 1. ОСНОВНЫЕ НАЧАЛА ТРУДОВОГО ЗАКОНОДАТЕЛЬСТВА</p>
<p class="H" id="p8">Статья 1. Цели и задачи трудового законодательства</p>
<p id="p9">Целями трудового законодательства являются ...</p>
```

| Класс | Значение |
|---|---|
| `p.T` | Заголовок части/раздела |
| `p.H` | Заголовок главы/статьи |
| `p.C` | Комментарий/справка |
| `span.mark` | Отметка о **действующем** изменении |
| `span.markx` | Отметка о **будущем** (не вступившем в силу) изменении |
| `span.ed` | Изменённый фрагмент внутри абзаца |
| `span.cmd` | Ссылка на акт-поправку, несёт `cmdprm="gohash=<dochash> goparaid=<id>"` |

### 3.5. Отметки об изменениях — точная привязка поправки к статье

```html
<p id="p2376">подготовке и дополнительному профессиональному образованию ...
  <span class="mark"> (В редакции Федерального закона
    <span class="cmd" cmdprm="gohash=c8c2e714...e313 goparaid=0 goback=1">от 02.07.2013 № 185-ФЗ</span>)
  </span>
</p>
```

`gohash` в `cmdprm` — это `dochash` акта-поправки. То есть, зная `eoNumber`
новой публикации, можно получить её `dochash` через `card/` и **найти в тексте
консолидированной редакции ровно те абзацы, которые этот закон изменил**, а по
ним — статьи.

**Внимание:** сопоставлять по номеру закона нельзя. В ТК РФ есть отметки и на
«от 31.07.2020 № 246-ФЗ», и на «от 26.07.2026 № 246-ФЗ». Номер повторяется в
разные годы. Сопоставлять только по `gohash`. Дополнительно: текст ссылки
содержит `&nbsp;`, поэтому сравнение строк требует нормализации — ещё одна
причина использовать `gohash`.

**Проверено сквозняком.** ФЗ от 26.07.2026 № 246-ФЗ, `gohash=797105...8dd0`,
редакция ТК РФ 495396 на 01.03.2027 — изменённые статьи:

```text
Статья 57     [future]  Содержание трудового договора
Статья 58     [future]  Срок трудового договора
Статья 59     [future]  Срочный трудовой договор
Статья 351.8  [future]  Особенности регулирования труда наставников
Статья 351.9  [future]  Особенности регулирования труда стажёров
```

Полный текст статьи 59 из этой редакции извлечён целиком — 5377 символов.

### 3.6. `getcontent/` — официальное структурное оглавление

```text
GET /api/ebpi/getcontent/?bpa=ebpi&rdk=<redid>
```

Для ТК РФ — 2479 узлов, `typeact: "кодекс"`:

```json
{"id":"b1_si_h1_a1", "np":"p8", "npe":"p2379", "unit":"статья",
 "caption":"Статья 1. Цели и задачи трудового законодательства", "lvl":3, "state":0}
{"id":"b1_si_h1_a1_c1", "np":"p9",  "npe":"p9",    "unit":"часть", "caption":"$часть 1", "lvl":4}
{"id":"b1_si_h1_a1_c2", "np":"p10", "npe":"p2379", "unit":"часть", "caption":"$часть 2", "lvl":4}
```

`np`/`npe` — **точные границы структурной единицы в виде id первого и последнего
абзаца** того же HTML, что вернул `redtext`.

Это означает: извлечение статьи — не regex и не эвристика по заголовкам, а срез
HTML по официальному структурному индексу. `unit` бывает `часть`, `раздел`,
`глава`, `статья` и `часть` внутри статьи — то есть гранулярность до части
статьи доступна бесплатно, хотя план выносил её за рамки MVP.

## 4. Что это меняет в архитектуре

Старая схема (из `IMPLEMENTATION_PLAN.md`, шаги 5–6): скачать PDF поправки,
`pdfplumber`, нормализация, regex по «Статья N», угадать дату вступления,
отдельно скачать консолидированную редакцию из другого источника и снова regex.
Плюс OCR для image-only PDF и LLM как fallback.

Новая схема — целиком детерминированная, без PDF, OCR, regex-разбора юридического
текста и LLM:

```text
1. publication.pravo /api/Documents  -> новые ФЗ за сутки (eoNumber)
2. ebpi card/?t={"pnum": eoNumber}   -> dochash акта-поправки
3. ebpi redactions/ по dochash отслеживаемого документа
       -> есть ли редакция, порождённая этим актом (reddocrefid / redcaption)
       -> reddate = дата вступления в силу
4. ebpi getcontent/?rdk=redid        -> структурный индекс (np..npe по статьям)
5. ebpi redtext?t=redid              -> HTML редакции
6. span.cmd[cmdprm~="gohash=<dochash>"] -> изменённые абзацы -> статьи
7. срез np..npe                      -> точный текст каждой изменённой статьи
8. legal_change (draft) на каждую статью, send_at = reddate
9. в reddate -> PUT в RAG Service
```

Дата вступления в силу берётся из `reddate` — официального поля, а не из разбора
формулировки «вступает в силу по истечении ста восьмидесяти дней». Набор
изменённых статей берётся из официальной разметки, а не из угадывания.

## 5. Ограничения, которые надо учесть

- Покрытие отметок об изменениях — с 01.07.2022 (`ACTUAL_START_DATE`).
  Для более ранних редакций `ttl=3` даёт список, но режим отметок иной.
- `redtext` для крупного кодекса — около 2 МБ на запрос. Кэшировать по `redid`,
  не тянуть повторно для каждой статьи одной редакции.
- Порт 8000 нестандартный — проверить, что он не режется файрволом прода.
- API недокументирован и реконструирован по фронтенду. Нужны контрактные тесты
  на фикстурах и явная ошибка при изменении структуры, а не молчаливый разбор.
- Один и тот же номер закона повторяется в разные годы — только `gohash`.
- `redcompleted`/`hascontent` могут быть `false` у свежих редакций: текст ещё
  готовится. Такое событие нельзя отправлять автоматически.
